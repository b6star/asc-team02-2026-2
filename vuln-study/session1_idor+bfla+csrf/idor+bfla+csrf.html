01 · IDOR 개념

IDOR(Insecure Direct Object Reference)

클라이언트가 전달한 객체 식별자를 서버가 권한 검사 없이 사용하는 취약점.

직접 객체 참조

사용자 ID, 주문 번호, 파일명처럼 서버의 특정 데이터를 가리키는 값.

/orders/1042
/files/report.pdf
/profile?user=42

취약점이 되는 조건

공격자가 식별자를 바꾸고, 서버가 요청자의 객체 접근 권한을 검사하지 않으면 허용되지 않은 데이터에 접근할 수 있다.

유형

수평적 권한 상승Horizontal Privilege Escalation
같은 권한 등급의 다른 사용자 객체에 접근.

수직적 권한 상승Vertical Privilege Escalation
상위 권한에만 허용된 객체에 접근.

식별자가 예측하기 어려워도 권한 검사는 필요. 객체를 읽거나 수정할 때 요청자와 대상 객체의 관계를 확인.

02 · BFLA 개념

BFLA(Broken Function Level Authorization)

사용자 역할에 따라 제한해야 할 기능을 서버가 검사하지 않는 취약점.

검사의 대상

IDOR는 “이 데이터에 접근할 수 있는가”를 묻는다.

BFLA는 “이 기능을 실행할 수 있는가”를 묻는다.

일반 사용자 → 관리자 기능 호출

자주 보이는 모습

관리자 메뉴를 화면에서 숨겨도, 기능 주소를 직접 호출하면 실행된다.

수직적 권한 상승Vertical Privilege Escalation
일반 권한에서 관리자 기능으로 접근.

메뉴 노출 여부와 서버 권한 검사는 별개. 관리자 페이지와 삭제 기능 모두 서버에서 권한을 확인.
02 · BFLA 문제 설명

03 · CSRF 개념

CSRF(Cross-Site Request Forgery)

인증과 인가가 통과한 사용자 세션으로, 의도하지 않은 상태 변경 요청을 보내게 하는 공격.

성립 조건

피해자가 대상 사이트에 로그인한 상태.

브라우저가 대상 사이트로 보내는 요청에 세션 쿠키를 자동 첨부.

서버가 요청 출처나 CSRF 토큰을 확인하지 않음.

요청 방식

HTML 폼은 GET과 POST 요청을 만들 수 있다. 상태 변경 기능은 주로 POST를 사용.

GET도 서버가 상태 변경에 사용한다면 공격 대상이 된다.

악성 HTML 또는 SVG(Scalable Vector Graphics)가 실행되는 맥락에서 폼 제출을 유도할 수 있다. 파일 업로드 자체는 별도의 조건을 따진다.

CSRF는 피해자의 로그인 세션을 이용해, 피해자가 의도하지 않은 요청을 웹사이트로 보내게 하는 공격이다.
03 · CSRF 문제 설명

피해자의 이메일을 바꾸는 Lab

CSRF vulnerability with no defenses

주어진 계정

wiener:peter로 로그인해 이메일 변경 기능을 먼저 확인한다.

POST /my-account/change-email email=test%40any.com

변경할 계정은 요청의 세션 쿠키로 결정.

해결 조건

같은 POST 요청을 자동으로 보내는 HTML을 Exploit Server에 저장.

내 계정에서 동작을 확인한 뒤 다른 이메일로 바꿔 피해자에게 전달한다.

05 · 정리

방어 기준

IDOR

객체를 읽거나 바꾸기 전, 요청자에게 그 객체의 권한이 있는지 확인.

BFLA

관리자 페이지를 열 때와 사용자 삭제 기능을 실행할 때 모두 관리자 권한을 확인한다.

CSRF

세션에 연결된 CSRF 토큰 검증. SameSite 쿠키와 Origin 검사는 보조 방어.

  1. CSRF 토큰(Cross-Site Request Forgery Token): 서버가 정상 페이지에 넣어주는 예측하기 어려운 값. 요청에 올바른 토큰이 없으면 서버가 거부한다.
  2. SameSite 쿠키: 다른 사이트에서 요청을 보낼 때 브라우저가 로그인 쿠키를 첨부하지 않도록 제한하는 쿠키 설정.
  3. Origin 검사: 요청이 어느 사이트에서 시작됐는지 확인하고, 허용된 사이트에서 온 요청만 처리하는 방식.
